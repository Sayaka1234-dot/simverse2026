# 机械臂台灯空间解谜：任务、数据集与评测说明

本文档详细介绍 `机械臂台灯空间解谜` 这个 2D Web 任务的玩法、关卡数据构造方式、数据集组织方式，以及模型评测时使用的指标与含义。

## 1. 任务概述

这是一个以“心理模拟”为核心的空间推理任务。玩家或模型不能直接拖拽机械臂，而是需要根据图中的几何关系，在脑中模拟多节机械臂的运动，然后为每一个关节输出一个绝对角度，让灯泡末端的照亮范围覆盖目标点。

任务的本质是一个离散化的正向运动学问题：

- 每一节机械臂都有固定长度。
- 每一节机械臂都有一个相对于 `x` 轴正方向的绝对角度。
- 所有关节角度不是累加关系，而是各自独立地相对于全局坐标系定义。
- 机械臂末端挂着灯泡，灯泡有固定半径的照亮范围。
- 当目标点落入照亮范围内时，该关卡判定成功。

## 2. 画面图例与玩法

在任务图片和游戏画面中，各个元素的含义如下：

- 白色线段：机械臂的杆。
- 蓝色小圆点：关节，也就是每一节杆的连接点。
- 黄色圆点：灯泡，位于最后一节机械臂的末端。
- 淡黄色半透明区域：灯泡的照亮范围。
- 橙色圆点：目标点，需要被照亮范围覆盖。
- 橙色菱形：机械臂底座，表示机械臂固定安装的位置。

玩家的操作方式不是拖动几何图形，而是为每个关节输入一个角度值。角度的语义是：

- 角度是相对于全局坐标系 `x` 轴正方向的绝对角度。
- 正角度表示逆时针旋转。
- 负角度表示顺时针旋转。
- 每节杆的角度都只描述“该杆所在直线”和正 `x` 轴之间的夹角。
- 第二节、第三节等后续机械臂的角度，不是相对前一节杆的相对角度。

例如，如果两节机械臂的角度分别是 `-90` 和 `-75`，表示：

- 第 1 节杆竖直朝下。
- 第 2 节杆也独立地相对正 `x` 轴指向 `-75` 度方向。

它不表示“第 2 节在第 1 节的基础上再转 `-75` 度”。

## 3. 胜利条件

系统会实时计算灯泡中心与目标点之间的欧氏距离：

```text
distance = sqrt((target_x - bulb_x)^2 + (target_y - bulb_y)^2)
```

如果：

```text
distance <= light_radius
```

则判定该关卡成功。

这意味着模型或玩家不需要把灯泡中心精确移动到目标点上，只要目标点落在灯泡的照亮圆范围内即可。

## 4. 几何与坐标系

项目里同时存在两个相关但不同的坐标概念：

- 坐标原点 `origin`：画布上的全局坐标原点，用来绘制网格与坐标轴。
- 机械臂底座 `arm base`：机械臂固定安装的位置，不一定和坐标原点重合。

在关卡 JSON 中：

- `workspace.origin` 决定“全局坐标原点”在画布像素空间中的绘制位置。
- `armBaseOffset` 表示机械臂底座相对于全局坐标原点的偏移。
- `target` 表示目标点在全局坐标系中的坐标。

因此，`target` 和 `armBaseOffset` 是同一套逻辑坐标系下的数据，可以直接用于评测。

正向运动学计算公式如下：

```text
x_0 = arm_base_x
y_0 = arm_base_y

x_i = x_(i-1) + length_i * cos(theta_i)
y_i = y_(i-1) + length_i * sin(theta_i)
```

其中：

- `theta_i` 是第 `i` 节杆的绝对角度。
- 最后一节计算得到的 `(x_n, y_n)` 就是灯泡中心位置。

## 5. 关卡数据如何构造

关卡文件存放在 `levels/` 目录，每个文件对应一关，例如：

- [lamp-000.json](../data/levels/lamp-000.json)

每个关卡大致包含这些字段：

```json
{
  "id": "level_001",
  "difficulty": 2,
  "workspace": {
    "width": 800,
    "height": 600,
    "gridSize": 40,
    "origin": { "x": 80, "y": 520 }
  },
  "lamp": { "lightRadius": 36 },
  "arm": {
    "segmentCount": 2,
    "segments": [{ "length": 90 }, { "length": 150 }],
    "initialAngles": [0, 0],
    "solutionAngles": [-120, 15],
    "angleStep": 15,
    "angleMin": -180,
    "angleMax": 180
  },
  "armBaseOffset": { "x": 40, "y": 40 },
  "target": { "x": 139.89, "y": 0.88 }
}
```

### 5.1 关卡生成流程

关卡由独立脚本随机生成，核心流程如下：

1. 随机决定机械臂节数，当前范围是 `1-3` 节。
2. 为每节机械臂随机选择长度，当前候选长度为 `90 / 120 / 150 / 180`。
3. 为每节机械臂随机选择一个绝对角度，步进为 `15°`，范围为 `-165°` 到 `180°`。
4. 随机选择全局坐标原点在画布中的位置。
5. 随机选择机械臂底座相对于原点的偏移 `armBaseOffset`。
6. 对随机出的“标准答案角度”做一次正向运动学计算，得到灯泡末端位置。
7. 将灯泡末端位置记录为该关卡的目标点 `target`。
8. 对关卡做合法性校验，不合法就重采样。

### 5.2 合法性校验

为了保证关卡可玩、可见、可解，生成器会检查这些条件：

- 全局坐标原点不能贴边。
- 机械臂底座不能跑出画布安全边界。
- 目标点不能跑出画布安全边界。
- 目标点不能离机械臂底座过近。
- 答案角度不能全部为 `0`。

由于目标点本身就是由标准答案正向推导得到的，所以每个被写入 `levels/` 的关卡天然都是可解的。

## 6. 数据集如何构造

为了做模型测评，项目会把 `levels/` 里的关卡进一步转换成数据集。数据集主要由三部分组成：

- `task/`：每关一条结构化任务数据。
- `images/`：每关一张初始状态截图。
- `task/manifest.jsonl`：枚举整个数据集。

### 6.1 task 文件

每个 `task/*.json` 文件都包含两层信息：

- `public`：模型可以看到的公开信息。
- `validator`：评测时使用的隐藏校验信息。

示例文件：

- [lamp-000.json](../data/levels/lamp-000.json)

`public` 中通常包含：

- `image`：对应初始状态截图路径。
- `target`：目标点坐标。
- `arm_base`：机械臂底座坐标。
- `segment_count`：机械臂节数。
- `segments`：每节机械臂的编号和长度。
- `lamp.light_radius`：照亮范围半径。
- `angle_constraints`：角度范围与步进约束。
- `coordinate_system`：坐标系规则说明。

`validator` 中通常包含：

- `source_level`：来源关卡文件。
- `solution_angles`：标准答案角度。
- `target`：用于校验的目标点。
- `arm_base`：用于校验的机械臂底座。
- `success_rule`：成功判定规则，目前为“距离小于等于半径”。

### 6.2 初始状态截图

`images/*.png` 中保存的是每关的初始状态截图，而不是解题后的截图。截图使用当前引擎直接渲染 Canvas 后导出，因此与实际游戏画面一致。

图片里通常展示：

- 坐标网格与坐标轴。
- 机械臂底座。
- 初始角度下的机械臂。
- 目标点。
- 灯泡和照亮范围。

这样做的目的是让模型同时具备：

- 视觉输入。
- 显式的结构化参数输入。

## 7. 模型输出格式

模型必须输出一个 JSON 对象，且顶层只能有一个键：`actions`。

格式如下：

```json
{
  "actions": [
    { "joint": 1, "angle": -120 },
    { "joint": 2, "angle": 15 }
  ]
}
```

输出约束如下：

- `joint` 从 `1` 开始编号。
- `actions` 的长度必须等于机械臂节数。
- 每个关节必须恰好出现一次。
- `angle` 必须是整数。
- `angle` 必须在该关卡允许的角度范围内。
- `angle` 必须满足步进约束，例如 `15°` 一档。

## 8. 验证器如何判题

评测过程分为两步：

### 8.1 格式验证

验证器会先检查模型输出是否满足 JSON 结构要求：

- 是否能从原始输出中提取出合法 JSON。
- 顶层是否只有 `actions`。
- `actions` 是否是列表。
- 数量是否与关节数一致。
- `joint` 是否覆盖 `1..N`。
- 是否有重复关节。
- `angle` 是否为整数。
- `angle` 是否满足上下界和步进要求。

如果格式验证失败：

- `is_valid_format = false`
- `evaluation_status = "format_error"`
- `is_valid_solution = false`

### 8.2 几何验证

如果格式验证通过，系统会把 `actions` 按关节编号排序，转换成标准化角度数组，然后交给引擎做正向运动学计算：

1. 从 `arm_base` 出发。
2. 按机械臂长度和角度计算末端灯泡位置。
3. 计算灯泡中心与目标点的距离。
4. 判断距离是否小于等于 `light_radius`。

如果通过几何验证：

- `is_valid_solution = true`

否则：

- `is_valid_solution = false`
- `solution_error` 会说明“灯光没有覆盖目标点”。

## 9. 单题结果文件包含哪些字段

每条评测结果会写入 `eval/results/<model>/<namespace>/<sample_id>.json`。

单题结果中的关键字段包括：

- `sample_id`
  当前样本编号，例如 `level_001`。

- `task_source`
  本次评测使用的任务文件路径。

- `model.model_name`
  被评测的模型名称。

- `raw_model_output`
  模型返回的原始文本。

- `normalized_answer`
  经过解析、排序、校验后的标准动作格式。

- `engine_result`
  引擎判题的详细结果。

- `evaluation_status`
  当前实现里常见取值有：
  - `ok`：格式通过，已进入几何验证。
  - `format_error`：格式未通过，无法进入几何验证。

- `is_valid_format`
  表示模型输出是否通过格式检查。

- `is_valid_solution`
  表示模型给出的动作是否真的解开了关卡。

- `distance`
  预测灯泡位置与目标点的欧氏距离。

- `task_metadata`
  数据集样本的附加信息，例如难度。

- `saved_at_utc`
  结果写入时间。

`engine_result` 内部还包含这些重要字段：

- `predicted_bulb`
  验证器根据模型答案计算出的灯泡坐标。

- `target`
  评测时使用的目标点坐标。

- `light_radius`
  判定半径。

- `normalized_angles`
  标准化后的角度数组。

- `format_error`
  当前实现里几何验证阶段通常为 `null`。

- `solution_error`
  若未命中目标，会给出失败原因。

- `is_pattern_correct`
- `is_pattern_and_rotation_correct`
- `is_fully_correct`

这三个字段目前与 `is_valid_solution` 保持一致，主要是为了兼容更通用的评测结果结构。

## 10. 汇总评测指标及其含义

汇总脚本会读取某个模型目录下的所有结果文件，输出整体统计。核心指标如下：

### 10.1 total_tasks

参与统计的总题目数。

### 10.2 valid_format_count

格式正确的题目数量。

它回答的问题是：

“模型能否稳定输出符合协议的 JSON 动作结构？”

### 10.3 valid_format_rate

格式正确率：

```text
valid_format_rate = valid_format_count / total_tasks
```

这个指标衡量的是模型的“协议遵守能力”，而不是解题能力。

### 10.4 solved_tasks

真正解开的题目数量，也就是 `is_valid_solution = true` 的样本数。

### 10.5 solution_rate

解题成功率：

```text
solution_rate = solved_tasks / total_tasks
```

这是最核心的任务指标，用来衡量模型整体是否能完成这个空间推理任务。

### 10.6 average_distance

所有有几何结果样本的平均距离。距离越小，说明模型给出的灯泡位置平均上越接近目标点。

这个指标有一个重要用途：

- 当 `solution_rate` 还不高时，它可以帮助判断模型到底是在“完全乱猜”，还是“已经接近正确，只差一点”。

### 10.7 median_distance

所有有几何结果样本的距离中位数。相比平均值，它更不容易被少量极端失败样本拉偏。

### 10.8 evaluation_status_counts

不同 `evaluation_status` 的分布统计。

当前实现里最常见的状态包括：

- `ok`：模型输出成功通过格式检查，并进入几何验证。
- `format_error`：模型输出在解析、字段、角度范围或步进约束上失败。

这个指标适合分析失败来源：

- 如果 `format_error` 很多，说明模型主要问题是输出协议。
- 如果大多数都是 `ok` 但 `solution_rate` 很低，说明模型会“说对格式”，但不会“解对几何题”。

## 11. 如何理解这些指标

这个任务的指标可以粗分成三层：

### 11.1 协议层

- `is_valid_format`
- `valid_format_rate`
- `evaluation_status_counts`

这层看模型是否能按要求输出规范动作。

### 11.2 几何层

- `distance`
- `average_distance`
- `median_distance`

这层看模型是否真的理解了空间关系，是否在逼近答案。

### 11.3 任务层

- `is_valid_solution`
- `solved_tasks`
- `solution_rate`

这层是最终任务表现，直接反映模型是否真正完成了“让灯光照到目标点”。

## 12. 一条样本的完整流转

一条样本从生成到评测，大致经过下面这条链路：

1. 生成器随机出机械臂长度、绝对角度答案、坐标原点和底座偏移。
2. 生成器做正向运动学，得到灯泡末端坐标，并写入 `levels/level_xxx.json`。
3. 数据集构建脚本把关卡转成 `task/level_xxx.json`。
4. 同时用引擎渲染出初始状态截图，写入 `images/level_xxx.png`。
5. 评测脚本把 `task` 和 `image` 发给模型。
6. 模型返回 `{"actions":[...]}`。
7. 验证器先做格式校验，再做几何校验。
8. 单题结果写入 `eval/results/...`。
9. 汇总脚本统计格式正确率、成功率和距离指标。

## 13. 总结

这个项目同时具备三种价值：

- 作为一个人类可玩的空间解谜小游戏。
- 作为一个结构清晰、可批量生成的数据集。
- 作为一个可复现实验流程的多模态空间推理评测基准。

它的核心难点不在于复杂物理，而在于：

- 理解图例。
- 理解绝对角度定义。
- 正确区分坐标原点和机械臂底座。
- 在离散角度空间中找到足够接近目标点的几何解。
